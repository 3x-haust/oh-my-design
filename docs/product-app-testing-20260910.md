# 제품과 모바일 앱 테스트 범위

사용자 요청: “모바일 "앱"도 테스트 해주고, 랜딩 말고 실제 제품도 테스트 해줘”.

## 결과 요약

두 공개 제품 시나리오를 OMD의 새 실행으로 시험했지만, 모두 생산 코드 생성 전에
막혔다. **새 제품의 동작·화면 품질은 미검증이며, 네이티브 모바일 앱 테스트도 미실행이다.**
규칙 검사 통과나 참고 사이트 캡처를 완성된 제품의 성공으로 계산하지 않는다.

| 대상 | 실행 결과 | 수행하지 못한 검증 |
| --- | --- | --- |
| 고객지원 콘솔 | 프레이밍·문구·일부 참고 측정 후 중단 | 검색·필터·답장·초안·완료/복구의 실제 사용, 최종 화면 평가 |
| 모바일 현장 점검 제품 | 프레이밍·문구 이후 필수 참고 검증 차단 | 390px 입력/오류 복구/저장, 1280px 관리자 검토 |
| 설치형 iOS/Android 앱 | OMD의 현재 네이티브 실행·증거 경로 없음 | 설치·탐색·키보드·재실행 후 상태 유지 |

실행 중 확인한 작업 ID 계약 충돌은 소스에서 수정했다. 별도의 참고 획득 문제와
브라우저 밖의 요구사항에 대한 증거 유형 문제는 남겨 두었으며, 새 소스로 제품 생성
전체를 재실행한 결과는 없다.

## 웹 제품 실행

기존 공개 회귀 시나리오 `evals/product-ux/prompts/01_support-console.md`를 수정 없이
새 빈 프로젝트에 입력했다. 대상은 고객지원 티켓 콘솔이다. 검색·상태/채널/담당자 필터,
대화와 답장, 초안 보존, 입력 오류, 완료·실행취소·재오픈을 실제로 수행하는 테스트다.
실제 고객 계정이나 운영 티켓에 접근하는 테스트가 아니다. 공개 시나리오이므로 미공개
평가나 인간 사용자 연구로 보고하지 않는다.

- 실행 디렉터리: `/private/tmp/omd-product-ux-20260910.svzTHz/support-console`
- 입력: 같은 상위 디렉터리의 `support-console-prompt.md`
- 실행 로그: 같은 상위 디렉터리의 `support-console-events.jsonl`
- OMD 실행 패키지: 앞선 전체 테스트를 통과한 동결 `runtime-13`
- 실행 상태: 생산 코드 없이 중단했다. Scout의 한 차례 단독 복구도 선택 가능한 참고
  조합을 만들지 못했다. 복구 역할 종료 후 코디네이터를 종료했으며, 강제 진행하지 않았다.

생성 후 코드를 루트에서 수동 보정하지 않는다. 제품의 첫 화면은 업무 대상과 다음 행동을
검사하고, 랜딩의 설득 구성이나 설치 CTA를 제품 평가에 적용하지 않는다. 동작의 성공과
시각적 품질은 별도로 보고한다. 결과물 없는 규칙 검사 통과는 제품 성공이 아니다.

## 모바일 앱의 현재 지원 경계

기존 `02_field-inspection-mobile.md`는 390px 브라우저와 1280px 관리자 화면을 검사하는
공개 회귀 시나리오다. 설치형 iOS/Android 앱 테스트를 뜻하지 않는다.

현재 `core/stack/shell.ts`의 실행 대상은 `browser`, `electron`, `tauri`뿐이다.
`core/design/index.ts`는 웹 앱 진입점과 빌드 설정을 찾고, 네이티브 프로젝트 판별은 없다.
`core/runtime/trusted-evaluation-plan.ts`는 고정 DOM 선택자로 행동과 결과를 도출한다.
따라서 현재 웹 렌더·브라우저 검사를 네이티브 모바일 앱 통과로 보고할 수 없다.

호스트에서는 Xcode 개발 경로, iPhone 시뮬레이터 목록과 iPhone Simulator SDK 26.2를
확인했다. 사용 가능한 iOS 시뮬레이터 런타임은 26.3이다. 이는 도구가 있다는 확인이며,
앱 설치·실행·탐색·키보드·재실행 후 상태 유지 테스트가 수행됐다는 뜻은 아니다.
특정 앱 지정 여부와 설치형 앱까지 필요한지 사용자에게 질문했으나 답변은 아직 없다.
별도의 iPhone 15 시뮬레이터 `OMD Product QA 20260910`을 생성·부팅했지만 앱 설치나
UI 조작은 수행하지 않았다. 실행 종료 시 이 장치가 `Shutdown`임을 확인한 뒤, 이번
검사용으로 만든 장치만 삭제했다. 설치 앱이나 사용자 데이터는 없었고 기존 사용자
장치는 변경하지 않았다. 네이티브 앱을 모바일 웹 화면으로 대체해 통과 처리하지 않는다.

두 범위에 공통인 모바일 제품 사용 흐름은 기존 `02_field-inspection-mobile.md`를
수정 없이 새 빈 프로젝트에 입력해 별도로 실행했다. 이 실행은 브라우저 프로토타입
테스트이며, 네이티브 앱 설치·실행 증거가 되지 않는다.

- 실행 디렉터리: `/private/tmp/omd-product-ux-20260910.svzTHz/field-inspection-mobile`
- 입력: 상위 디렉터리의 `field-inspection-prompt.md`
- 실행 로그: 상위 디렉터리의 `field-inspection-events.jsonl`
- 핵심 검사: 10개 중 7개 부분 입력, 누락한 3개 항목 지목, 기존 입력 보존,
  이상 항목의 우선순위·조치 요청, 로컬 보존 안내, 완료 후 관리자 검토
- 실행 상태: OMD 역할에서 필요한 대화형 브라우저 검증을 사용할 수 없어 참고 조합과
  선택을 완료하지 못했다. 호스트 프로세스는 정상 종료했지만, 과제 결과는 미완료다.
  `field-inspection-result.md`에 이 실패가 기록되어 있다. 생산 코드와 행동 결과는 없다.

두 실행의 입력은 저장소의 공개 시나리오와 바이트 단위로 일치함을 확인했다. 생성한
결과를 보고 시나리오나 합격 기준을 바꾸지 않는다.

## 실행한 하네스 회귀 검사

`app-shell`, `stack`, `product-surface`, `trusted-evaluation-plan`의 기존 검사 28개는
모두 통과했다. 결과는 상위 실행 디렉터리의 `product-preflight-tests.log`에 있다.
이 검사는 웹/데스크톱 앱의 기존 분기와 제품 평가 계획을 확인한다. 네이티브 모바일
앱 지원이나 새 콘솔의 디자인·행동을 증명하지 않는다.

## 실행 중 관찰한 준비 단계 문제

지원 콘솔의 `route classify`는 12회 실패 후 13번째 호출에서 통과했다. 공개 실행 로그의
`item_19`부터 `item_61` 사이에서 확인했다. 필수 방법 누락, reference work 불일치,
제품 task-flow 단계 누락, 알 수 없는 단계명, 명령 형식 오류가 포함된다. 특히 동일한
task-flow 단계 누락 오류 뒤에 단계명을 추측하는 재시도가 반복됐다.

이는 생성 결과의 시각적 실패 수나 제품 사용자의 행동 오류 수가 아니다. 작성된 실행
설정과 하네스 안내·검증 사이에서 관찰한 준비 단계의 재시도 비용이다. 유효한 설정으로
통과한 이후의 제품 생성·동작·시각적 결과와 분리해 보고한다. 원인 확인 없이 검사 자체를
완화하거나 입력을 루트에서 수동 고쳐 시험을 통과시키지는 않았다.

## 재현 후 수정한 작업 ID 충돌

프레이밍과 작업 흐름 벤치마크는 정규 작업 ID `T2` → `T3`를 사용했지만,
`entry-surface-contract`는 소문자 kebab-case만 허용했다. Framer의 실제
`frame set … --entry-surface -` 호출은 `MALFORMED_ENTRY_SURFACE_CONTRACT`로
실패했다. 기존 프레임은 변경되지 않았다.

- `core/frame/entry-surface-contract.ts`: 기존 의미형 ID와 `T` 뒤에 0으로 시작하지 않는 숫자가
  오는 정규 ID를 함께 허용하고
  기존 64자 제한을 유지하는 판별 함수를 공유한다.
- `core/runtime/observation.ts`: 같은 판별 함수를 두 작업 ID 필드에만 사용한다.
  일반 텍스트와 민감 키의 가림 처리는 유지한다.
- `core/schema/inputs.ts`: 벤치마크 ID를 개명하지 않고 그대로 사용하도록 안내한다.
- `test/trusted-evaluation-plan.test.ts`: 정규 ID 성공, 잘못된 대문자/선택자/길이 거절,
  긴 ID의 제한적 보존, 실제 브라우저 실행과 위조 계획 거절을 검사한다.

수정 전 새 검사 세 개가 실패했고(`task-id-red.log`), 수정 후 해당 파일의 여덟 검사가
통과했다(`task-id-green.log`, 실패·건너뜀 0). `T2` → `T3`와 기존 의미형 ID 양쪽으로
실제 브라우저 회귀를 수행했다. 이는 평가기 회귀 검사이지 새 고객지원 제품의 사용
검사가 아니다. 타입 검사와 빌드도 통과했다. 전체 `npm test`는 2,550개 중 2,548개
통과, 실패 0, 건너뜀 2로 종료했다(651.4초). 전체 출력은 `full-tests.log`에 있다.
이 회귀 통과는 위의 제품 생성 실패나 모바일 앱 미실행을 해소하지 않는다.

## 수정하지 않은 차단 원인

1. **참고 상태 획득.** 지원 콘솔은 단독 복구에서도 실제 상담원 메시지, 완료 후 복구,
   모바일 대기열·복합 필터 상태의 근거가 부족했다. Scout는 실제 측정한 원시 동작과
   제품에서 구현해야 할 동작을 분리하는 Framer 수정안을 반환했으나 계획을 임의로
   고치지 않았다. `scout.md`에 성공 캡처, 실패, 수정 제안이 남아 있다. 캡처 간격 감사도
   실패했으며, 이것을 제품 UI 결함이나 독립된 사용자 실패로 계산하지 않는다.
2. **화면 밖 요구사항의 증거 유형.** 지원 콘솔의 17개 요구사항에는 생산 코드 작성
   주체 제한과 두 Eye의 리뷰·최종 실행 검사가 포함돼 있다. 현재 entry witness는 모든
   요구사항을 보이는/없는 텍스트로만 증명하도록 요구한다. 화면 텍스트로 작성 주체나
   독립 리뷰를 증명할 수 없다. 요구사항을 삭제하거나 텍스트 대리 증거를 만들어 통과
   시키지 않았다. Framer의 서명된 `framer-entry-role-result.json`과 현재 스키마에
   이 불일치가 기록돼 있다. 항목별 증거 유형과 별도 검증 경로의 설계가 필요하다.
3. **네이티브 모바일 경로 부재.** 시뮬레이터 설치 여부와 별개로 OMD에 네이티브
   프로젝트 실행·조작·검증 연결이 없다. 390px 브라우저 테스트로 이 경계를 지우지 않는다.

추가 작업은 우선 사용자 요구사항을 보존하면서 브라우저 행동, 파일/작성 권한,
독립 리뷰의 증거를 각각 맞는 검증기로 연결하는 계약을 설계하는 일이다. 이는 이번
ID 파서 수정과 다른 범위이므로 이 실행에서 임의로 구현하지 않았다.
