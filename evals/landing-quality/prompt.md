# OMD landing page: supplied visual ambition

Build a complete, working landing page for Oh My Design (OMD), the design harness in this
repository. Use OMD's native adaptive workflow and its source-owned skills. This is a public
development fixture, not a held-out evaluation. Do not use paperthin or any other external harness.
Use only the OMD skills shipped with this run's package. Do not load or invoke any other personal
skill, including UI instruction boundary, work, re0, sip, shower, or Ouroboros, even if a global
skill catalog offers one. Handle copy boundaries and verification through OMD's own contracts.
This restriction applies to the coordinator and every delegated role.

The four project-owned PNGs in `inputs/` are the user's minimum visual-quality examples:
`cut-and-reassemble.png`, `cut-and-reassemble-mobile.png`, `index-as-interface.png`, and
`living-wordmark.png`. Inspect all four before making a visual decision. They calibrate ambition,
conceptual specificity, typography, composition and finish. The user has not selected one as a
literal reproduction target. A new direction may depart from their palette and layout. The page
must be built as accessible HTML/CSS/JS; the concept PNGs are not page imagery to embed.

The audience is developers who use coding agents and want more deliberate interface design. Use
English, as in the supplied studies, with mechanics-only locale treatment and no market-specific
cultural claim. Build one responsive page at `index.html` with local CSS/JS/assets as needed.
No framework or third-party runtime dependency is needed. Preserve all input images unchanged.

## Product facts

The following facts are grounded in the repository's current README and source, and are sufficient
first-party product material for this fixture:

- Product name: Oh My Design. Short name: OMD.
- It is a design process for coding agents. It runs in Codex, Claude Code and hosts implementing
  the public Pi extension API.
- The task outcome, facts, risk and available evidence select the methods. Selected work can
  include framing the brief, collecting references, writing real copy, proving typography,
  composing alternatives, building, inspecting browser renders, and repairing from evidence.
- It keeps a durable project record in `.omd/` and uses independent review of rendered output.
- The model is the user's choice. The harness does not silently substitute another model.
- The scoped package installation command is `npm install -g @3xhaust/oh-my-design`.
- After installation, `oh-my-design install` installs the host integration, and `omd doctor`
  checks the runtime. Node.js 22.19 or newer is required.
- Source and documentation: `https://github.com/3x-haust/oh-my-design` and
  `https://github.com/3x-haust/oh-my-design#readme`.

Do not invent customers, endorsements, performance statistics, awards, prices or evidence of
human-equivalent results. Do not present every optional method as a compulsory sequence.
Write reader-facing copy from these facts. Process instructions in this brief are not UI copy.

## Required outcomes

A visitor can identify what OMD does, understand how its process helps interface work, copy the
exact installation command, find the next setup step, and open source/documentation links.
Use a real clipboard action with success feedback only after a successful write and an accessible
select-and-copy recovery when clipboard access fails. If a navigation menu is introduced, it must
work with keyboard and touch, expose its state, and close predictably. All actual links must lead
to real sections or the supplied destinations.

The beginning, middle and end should follow one content-grounded visual idea. Carry the concept
into the explanation and installation flow, not only the hero. Plan useful visible experiments
before committing to an unsettled idea; their count and method follow the actual uncertainty.
Judge the experiments from renders before choosing. A missing image-generation capability does
not prevent OMD's supported HTML study method. Do not turn the examples into a mandatory style.

## Evidence and completion

Inspect fixed desktop 1280×900 and mobile 390×844 renders, plus full-page continuity. Also check
320 px reflow, 200% zoom, keyboard focus, clipboard success/failure, reduced motion and no-JS
content reach. These are local user-interface actions; no remote posting, publishing or account
changes are part of the task. Use the native renderer and actual browser actions for the selected
trusted evidence path. A DOM assertion alone does not demonstrate visual quality.

The reference images are ambition material for production decisions. Independent final reviewers
receive anonymous production renders, the bounded task and factual constraints, and current
behavior evidence. They do not receive reference PNGs, concept names, author rationales, prior
verdicts or desired scores. Preserve disagreements and repair actual weaknesses. Native final
evidence and terminal preflight remain required; intermediate studies or a successful owner
transaction do not constitute completion.

Return the runnable page path, exact evidence paths, actual checks and remaining blockers. Keep
all work inside the target fixture project. Do not edit the OMD package, global host settings,
other projects, or the user's older design records. Do not commit, publish or deploy the page.
